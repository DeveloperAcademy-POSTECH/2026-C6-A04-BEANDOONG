# 스티밍 소리 모델 v3.5

## v3.5 업데이트 (2026-11-09)

2026-11-08 추가 데이터 재학습 후보(`ModelRefresh20261108R2/models/iteration3`)의 스티밍 분류 모델을 적용하고 자동 종료를 연결했습니다. 버전은 v3.5이며 Swift·리소스 이름에는 `V3_5`를 사용합니다. 기존 v3.0 모델 파일은 앱 번들에서 교체합니다. 분류 구조를 시간 특징 후보로 바꾸지 않고 현재의 게이트→공기주입/쇳소리 갈래를 유지합니다.

- 스티밍 분류: `ChicModelV3_5Gate`, `ChicModelV3_5Air`, `ChicModelV3_5Metallic`.
- 재학습 입력과 맞추기 위해 모든 갈래가 **고역 강조 없는 원음 특징 273개**를 공유합니다. 기존 11~12kHz +7dB 필터는 분류에 적용하지 않습니다.
- 공기주입 갈래의 파바박 문턱은 0.5, 쇳소리 갈래는 쇳소리가 최댓값이면서 0.65 이상이어야 합니다. 게이트의 숨소리·휘파람은 기타로 처리합니다.
- 표시는 현재 앱의 **10프레임 최다 집계, 공기주입 1묶음·롤링 2묶음·쇳소리/파바박 3묶음 연속**을 유지합니다. 초기 기타만으로는 피드백 화면으로 전환하지 않습니다.
- 종료 감지는 작업 점수·종료음·청소음 점수를 함께 내는 재학습 4분류 모델을 사용합니다. 기존 실험의 별도 공기주입/롤링 이력 분류기는 앱에 넣지 않습니다.

### 종료 분류 리소스 통일

최초에는 종료 분류의 JSON 계수와 Swift 내적·softmax 구현을 `ChicEndV3_5.mlmodel`로 통일했습니다. 아래 추가 수정에서는 0.5초 입력으로 재학습한 부스팅 분류기로 같은 리소스를 교체했습니다. 특징 추출과 시간 이력 관리는 기존 코드에 남으며, 61탭 FIR은 학습 계수가 아닌 고정 전처리 상수로 보관합니다. 분류 모델은 CPU에서 실행합니다. 파일 형식 변경 자체로 정확도·속도·메모리가 개선되는 것은 아닙니다.

### 짧은 입력과 문턱 수정 (2026-11-09)

종료 모델의 현재 소리 입력을 0.975초에서 0.5초로 줄이고, 동일한 최신 125개 학습 출처 자료로 재학습했습니다. 작업 중 분류 모델 3개는 그대로입니다. 종료 입력 특징은 현재 Apple 특징 512개·직전 5/15회 대비 변화 1,024개·주파수 변화 309개로 총 1,845개를 유지합니다. 0.5초는 현재 소리 특징 입력 길이이며 과거 변화 특징의 보관 기간까지 0.5초라는 뜻은 아닙니다.

종료 분류는 깊이 3·최대 잎 7·100회 부스팅을 Core ML 트리→softmax 파이프라인으로 저장합니다. JSON 학습 가중치나 앱 내 직접 분류 계산은 없습니다. 같은 데이터에서 재학습한 약 0.139/0.245/0.459초 주파수 후보와 0.5초 선형 후보는 비교 자료에 남기고 채택하지 않았습니다.

종료 문턱을 0.995에서 0.8로 낮추면서 실제 원음의 3dB 감소를 추가 확인합니다. 점수만 낮추는 후보의 작업 중 충돌 때문에 추가한 보조 조건이며, 기계음만 분리하거나 모든 종료음에 보편적으로 성립한다고 가정한 조건은 아닙니다. 3dB는 현재 묶음 RMS와 직전 10묶음의 평균 제곱 에너지를 비교합니다. 청소음 문턱은 0.995 1회에서 0.5 5회 연속으로 바꿉니다. 활성화 기준과 작업 점수 <0.3 20회 조건은 유지합니다.

출처 분리 개발 자료에서 종료음 경로 12/33→19/33, 청소음 경로 3/17→9/17을 확인했습니다. 새 종료음·청소음 경로의 작업 라벨 충돌은 각각 0회였지만, 기존 작업 점수 기반 소멸 경로를 포함한 전체 비교에는 8회 충돌이 남았습니다. 이 자료는 입력·문턱 선택에 재사용했으므로 새 독립 정확도나 실기기 성공률로 해석하면 안 됩니다. 이전 미학습 영상 5개 종료 참고 구간에서는 세 경로 합계가 1/5→2/5였고, 3개 구간은 여전히 놓쳤습니다. 전체 해결이나 범용 정확도를 보장하지 않습니다.

## 시작과 종료 기준

**시작은 연습 버튼을 누른 시점이 아니라, 기존 `ChicDisplayFilter`가 첫 피드백을 확정하여 소리 확인 중 화면에서 벗어나는 시점입니다.** 그 묶음까지의 종료 점수와 낮은 작업 점수는 종료 판단에 사용하지 않습니다. 다음 묶음부터 종료 감지를 허용하며 추가 고정 대기시간은 없습니다. 작업 점수 0.5 이상 20회로 다시 활성화하는 조건과 별도의 공기주입→롤링 이력 조건은 제거했습니다.

| 우선순위 | 종료 경로 | 조건 |
|---|---|---|
| 1 | 종료음 | 종료음 점수 ≥0.8, 최근 원음 RMS가 직전 10묶음 평균 에너지보다 ≥3dB 감소, 1회 |
| 2 | 소멸 | 작업 점수 **<0.3, 20회 연속** 또는 실제 원음 RMS **<−55dBFS, 20회 연속** |
| 3 | 청소 방출음 | 청소 점수 ≥0.5, 5회 연속 |

세 경로는 OR 조건입니다. 같은 시점에 겹치면 표의 우선순위로 한 번만 종료합니다. 종료음이나 청소음을 기다리느라 다른 경로를 지연시키지 않습니다. 작업 점수가 **정확히 0.3이거나 더 크면 소멸 횟수를 0으로 초기화**합니다. 이 조건의 소멸은 실제 기계음 분리를 뜻하지 않으며, 이전의 주파수 성분 9dB 감소 조건을 함께 요구하지 않습니다. 청소음은 점수 0.5 이상 5회 연속으로 확인하며 한 번이라도 0.5 미만이면 초기화합니다. 첫 양성부터 다섯 번째까지 약 0.427초이고 5묶음 분량은 약 0.533초입니다.

종료 모델은 원시 10프레임마다 약 106.667ms에 한 번 실행합니다. 20회 연속의 첫 양성부터 마지막 양성까지는 약 2.027초이며, 20묶음 길이로는 약 2.133초입니다. 입력 문맥과 마이크 버퍼 때문에 실제 소리 변화부터의 지연과는 다릅니다. 0.3 미만을 띄엄띄엄 20번 누적하지 않습니다.

## 앱 연결과 저장

`SteamingAudioAnalyzer`가 마이크 입력을 직렬 분석 큐에서 처리하고 첫 피드백에 종료 규칙을 활성화합니다. 종료가 확인되면 분석 큐의 후속 결과를 폐기하고 `onFinish`를 전달합니다. `PracticeSession`은 세션 ID가 현재 연습과 같은지 확인한 후 기존 `stop()`을 호출합니다. 따라서 자동 종료도 수동 정지와 같은 결과 저장·결과 화면·워치 동기화 경로를 사용합니다. 중복 저장은 기존 실행 상태 검사로 막습니다. 새 연습은 새 분석기·종료 횟수·특징 이력을 사용하며 마이크 원음은 저장하지 않습니다.

## 종료 모델 입력

`ChicEndDetector`는 기존 작업 분류가 계산한 FFT를 공유합니다. 추가 FFT나 별도 마이크 탭을 만들지 않습니다.

1. 48kHz 원음을 학습 때 사용한 61탭 인과적 FIR로 16kHz로 줄입니다.
2. 묶음 끝 시각의 최근 8,000샘플(0.5초)을 `ChicAudioFeatures`에 넣어 Apple AudioFeaturePrint 512개를 추출합니다. 시작 시 부족한 앞부분은 학습과 같이 0으로 채웁니다.
3. 정규화된 현재 특징과 직전 5·15묶음 대비 차이 1,536개, 직전 3·10·30묶음의 스펙트럼 변화 309개를 합칩니다.
4. `ChicEndV3_5.mlmodel`에 재학습한 부스팅 트리와 softmax를 포함해 Core ML로 기타/작업/종료/청소의 네 점수를 계산합니다.

시작 전에도 특징 이력은 유지하지만 종료 규칙은 비활성입니다. 실행 중에는 최근 입력창·최대 15개 특징 벡터·30개 대역 벡터만 유지합니다. 모델 추론과 상태는 동일 큐에 한정합니다. 입력 오류·모델 불일치는 기존 분석 오류 처리로 종료하고 안내합니다.

## 실제 저음량 종료 보완 (2026-11-09)

작업 점수와 별도로 변환된 48kHz 원음의 최근 5,120샘플 RMS를 계산합니다. 첫 피드백 뒤 −55dBFS 미만이 20회 연속이면 작업 점수와 무관하게 소멸로 종료합니다. −55dBFS 이상이면 저음량 횟수만 초기화합니다. 작업 점수 저하와 저음량을 번갈아 채워 20회로 합치지 않습니다. dBFS는 입력 디지털 진폭이며 현장 음압이 아닙니다.

기존 작업 녹음 8초 뒤 −70dBFS 잡음을 붙인 제어 실험에서 기존 모델은 이후 작업 점수 중앙값 약 0.63으로 종료하지 못했습니다. 보완 후 −60·−70·−80dBFS 잡음에서 전환 2.165초 후 종료했습니다. 현재 125개 출처 자료의 작업 라벨에서는 −55dBFS 미만 20회 연속이 없었고, −50dBFS는 작업 라벨 한 파일과 충돌했습니다. 이는 실기기 마이크나 미라벨 구간의 안전성을 검증한 결과가 아닙니다. 입력 게인·거리별 확인이 필요합니다.

DEBUG 빌드는 활성화 상태·네 점수 중 작업/종료/청소·RMS를 `SteamingEnd` 로그에 기록합니다. 자동 종료 시에는 사유와 점수를 기록하며 소리 원본은 저장하지 않습니다.

# 스티밍 소리 모델 v3

연습 시작 시 `PracticeSession`이 `SteamingAudioAnalyzer`를 시작합니다. 소리 원본은 저장하지 않으며, 분석 결과는 기존 `updateFeedback(_:)`를 통해 iPhone 화면과 워치에 전달합니다. 정지·오디오 중단·분석 오류가 발생하면 분석도 종료하고, 늦게 도착한 이전 연습 결과는 세션 ID로 무시합니다.

## v3 업데이트 (2026-11-06)

재학습 모델 3개와 10프레임 최다 집계·연속 판정 규칙을 적용했습니다. 모델 리소스와 로더 이름은 `ChicModelV3`로 변경했습니다. 입력 변환·특징 추출·강조 필터는 변경하지 않아 `ChicV2` 이름의 공통 구현을 그대로 사용합니다.

- 검수 완료된 추가 기계 녹음 16개와 포항공과대학교 8·9의 숨소리·휘파람 녹음 2개를 학습 전용으로 추가했습니다. 새 자료는 검증에 넣지 않았습니다.
- 기존 추가 학습 규칙에 따라 총 4,327개 표본을 사용했습니다: 공기주입 1,490, 쇳소리 348, 파바박 182, 기타 1,939, 숨소리·휘파람 368개입니다. 미검수 36개와 충분한 특징 이력을 확보하지 못한 짧은 라벨 구간 6개는 제외했습니다.
- 게이트에는 5개 라벨을 모두 추가했습니다. 공기주입 헤드에는 공기주입·파바박만, 쇳소리 헤드에는 숨소리·휘파람을 `other`로 매핑해 추가했습니다.
- 기존의 **100ms마다 마지막 판정 하나 + 최근 4표 중 3표/3표 중 2표**를 **10프레임 최다 판정 + 공기주입 1회·롤링 2회·경고 3회 확인**으로 교체했습니다.

## 모델과 분석 흐름

- `chic/Models/ChicModelV3Gate.mlmodel`: 공기주입 계열 여부와 숨소리·휘파람 반례를 판단하는 1단계 모델
- `chic/Models/ChicModelV3Air.mlmodel`: 공기주입 계열의 정상/파바박을 구분하는 2단계 모델
- `chic/Models/ChicModelV3Metallic.mlmodel`: 그 밖의 소리에서 쇳소리를 구분하는 2단계 모델
- `Services/SoundAnalysis/ChicV2Input48k.swift`: 마이크 PCM을 48 kHz 모노로 변환
- `Services/SoundAnalysis/ChicV2Filter.swift`: 1단계에만 11–12 kHz를 7 dB 강조
- `Services/SoundAnalysis/ChicV2FeatureExtractor.swift`, `ChicV2SpectralFeatures.swift`: 원음·강조음의 특징 273개를 각각 계산
- `Services/SoundAnalysis/ChicModelV3.swift`: 두 단계 분기와 모델 추론
- `Services/SoundAnalysis/ChicDisplayFilter.swift`: 10프레임 집계와 연속 판정에 따른 표시 전환
- `Services/SoundAnalysis/SteamingAudioAnalyzer.swift`: 마이크 입력을 분석 큐에 전달하고 결과를 화면 상태로 변환

원음과 강조음은 같은 마이크 버퍼에서 만들어집니다. 1단계는 강조음, 2단계는 같은 시점의 원음 특징을 사용합니다. 공기주입 갈래는 파바박 점수가 `0.7543236034777003` 이상일 때만 `sputter`입니다. 1단계의 `breath_whistle`은 바로 `other`로 처리합니다. 2048샘플 창·512샘플 간격과 필터·특징 이력은 연습이 끝날 때까지 유지됩니다.

| 최종 출력 | 기존 상태 | 화면 |
| --- | --- | --- |
| `air` | `aeration` | 정상 공기주입 |
| `sputter` | `bubble` | 큰 기포 주의 |
| `metallic` | `moreAir` | 공기 주입 부족 |
| `other` | `listening` / `milkFlow` | 첫 스티밍 소리 확인 전에는 소리 확인 중, 이후에는 롤링 |

화면과 워치에는 `ChicDisplayFilter`가 확인한 같은 상태를 보냅니다. 최종 모델 판정 10개를 겹치지 않는 묶음으로 모아 가장 많이 나온 상태를 대표 판정으로 사용합니다. 동률이면 동률 상태 중 가장 최근 프레임의 상태를 선택합니다. 묶음이 완성되기 전에는 새 표시를 내보내지 않습니다.

| 표시할 상태 | 필요한 대표 판정 |
| --- | --- |
| 공기주입 `air` | 공기주입 1회 |
| 롤링 `other` | 기타 2회 연속 |
| 쇳소리 `metallic` | 쇳소리 3회 연속 |
| 파바박 `sputter` | 파바박 3회 연속 |

연속 횟수는 원시 프레임이 아닌 **10프레임 집계 후 대표 판정**을 셉니다. 다른 판정이 나오면 그 판정의 1회부터 다시 세며, 공기주입과 파바박을 합산하지 않습니다. 예를 들어 `쇳소리→쇳소리→공기주입→쇳소리`는 쇳소리 3회로 인정하지 않습니다. 조건을 충족하기 전에는 직전 표시를 유지합니다. 새 연습은 소리 확인 중에서 시작하고, 초기 `other`만으로 롤링 화면을 띄우지 않습니다.

대표 판정 주기는 `10 × 512 / 48,000`, 약 106.7ms입니다. 시작부터 같은 상태를 계속 판정하는 경우 첫 공기주입 표시는 약 138.7ms, 첫 경고 표시는 약 352ms 시점에 가능합니다. 마이크 버퍼 도착·모델 문맥·오판·UI 처리로 실제 표시는 더 늦어질 수 있습니다. 별도 최소 유지시간이나 강제 전환 타임아웃은 없으므로 연속 조건을 충족하지 못하면 기존 화면을 계속 유지합니다.

필터의 묶음과 연속 횟수는 마이크 버퍼 경계를 넘어 유지됩니다. 새 연습은 새 분석기·필터를 만듭니다. 피드백 화면 전체 전환에는 애니메이션을 쓰지 않습니다. `other`에는 일반 롤링 외의 비스티밍 소리도 포함될 수 있습니다. 분석 오류는 롤링으로 숨기지 않고 연습을 종료하며 안내합니다.

## 선택 근거와 한계

아래 평가는 공기주입도 2회 연속 확인하던 시점의 결과입니다. 공기주입을 1회로 줄인 현재 규칙의 정확도와 실기기 반응 시간은 별도로 측정해야 합니다.

개발 녹음 28개에서 10~15프레임을 비교한 뒤 10프레임으로 고정하고 기존 검증 녹음 44개에서 확인했습니다. 10개와 11개의 공기주입·롤링 종합 점수 차이는 약 0.09%p였고 10개가 더 빨랐습니다. 12~15개는 전환 횟수를 더 줄였지만 일부 구간에서 연속 조건의 충족이 늦어졌습니다. 새 학습 자료와 출처가 겹치는 검증 3개는 제외했습니다.

아래 기준선은 **같은 재학습 모델에 이전 표시 규칙을 적용한 결과**이며, 예전 앱의 다른 모델 가중치와 직접 비교한 결과가 아닙니다. 정답률은 수동 라벨 구간에서 해당 화면이 표시된 시간 비율입니다.

| 지표 | 이전 표시 규칙 | v3 |
| --- | ---: | ---: |
| 공기주입 정답률 | 72.3% | 76.9% |
| 롤링 정답률 | 82.6% | 82.0% |
| 쇳소리 정답률 | 50.2% | 46.6% |
| 공기주입 중 쇳소리·파바박 오표시 | 3.58% | 2.26% |
| 같은 정답 구간 내 화면 전환 | 409회 | 392회 |

경고를 더 엄격하게 확인하므로 짧은 경고를 놓칠 수 있습니다. 별도 희귀 파바박 5구간은 기존 4개 누락에서 v3는 5개 모두 누락했습니다. 일반 검증의 파바박도 4구간뿐입니다. 검증 자료를 반복 사용한 설계 비교이며 새 독립 테스트에서의 성능을 보장하지 않습니다.

100ms 마이크 버퍼 도착을 가정한 보조 계산에서는 최초 표시의 추가 지연 중앙값이 공기주입 0ms, 롤링 +100ms, 쇳소리·파바박 +200ms였습니다. 실제 기기에서 측정한 지연이 아닙니다.

1. 워치 없이 연습을 시작하고 공기 주입·쇳소리·버블·그 외 소리를 들려줬을 때 각 화면이 바뀌는지 확인합니다.

3. 워치와 연습할 때 같은 상태가 전달되는지, iPhone에서 종료하면 분석이 멈추고 워치에도 종료 화면이 표시되는지 확인합니다.
